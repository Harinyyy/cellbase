# Cell Culture Laboratory Management Platform — Revised MVP Architecture (v2)

**Scoped strictly to the assignment brief:**
> "Cell culture laboratories require monitoring of incubators, media preparation, culture schedules, contamination logs, and experiment tracking. The platform digitizes laboratory operations."

Core modules: **Authentication, Dashboard, Incubator Monitoring, Media Preparation, Cell Culture Management, Culture Scheduling, Contamination Logs, Experiment Tracking, Experiment Observations.**

Removed from v1: equipment booking, centrifuges/biosafety cabinets, generic multi-type reagent inventory, freezer/storage-location management. Cell line/passage concepts are kept only in the minimal form needed to support Cell Culture Management — no separate inventory/lot-tracking system around them.

```
                                                               │
                                          ┌─────────────────────┼─────────────────────┐
                                          ▼                                          ▼
                                ┌──────────────────┐                     ┌──────────────────┐
                                │   MongoDB       │                     │      Redis         │
                                │  (all persistent    │                     │  (session store,    │
                                │   lab records)       │                     │  alert cache,        │
                                │                     │                     │  dashboard cache)   │
                                └──────────────────┘                     └──────────────────┘
```

Unchanged principles: single backend monolith (module-per-domain internally), MongoDB as sole source of truth, Redis used for a small number of concrete, demonstrable jobs (not decoration), everything brought up with one `docker compose up`, source controlled in Git/GitHub with a normal feature-branch + PR workflow (no CI/CD pipeline required for MVP).

## 3. MongoDB Collections & Relationships

The backend uses MongoDB through Mongoose. To preserve the existing REST contract, documents retain numeric `id` fields generated by an atomic counters collection. Related records use numeric references, validated by the services. Passage history is embedded in each culture document, and observations are embedded in their experiment document. Other records are stored in their own collections.

### Collections

- `users`: full name, unique normalized email, password hash, role, and creation timestamp.
- `incubators`: name, target environment, status, and creation timestamp.
- `incubator_readings`: incubator reference, measurements, recorder reference, and timestamp.
- `media_batches`: preparation data, volumes, expiry date, notes, and preparer reference.
- `cell_cultures`: culture identity, incubator reference, passage counter, status, starter reference, and embedded `passages` history.
- `culture_schedules`: culture reference, task type, scheduled time, assignee, status, and notes.
- `contamination_logs`: culture reference, reporter, description, detection time, resolution notes, and status.
- `experiments`: culture reference, title, objective, dates, status, creator, and embedded `observations`.
- `counters`: atomic numeric ID sequences for the REST resources.

The service layer retains the prior lifecycle behavior: deleting an incubator removes its readings and clears culture assignments; deleting a culture removes schedules and contamination logs but is blocked while experiments reference it; deleting a user clears audit references and protects the last admin account.

**Data migration:** switching from PostgreSQL does not automatically convert the existing database. The old PostgreSQL data directory remains untouched; records must be explicitly exported and imported if they need to carry over.
## 4. REST API Endpoints

Base path `/api/v1`, JWT bearer auth on all routes except `/auth/*`.

### Auth
| Method | Endpoint | Purpose |
|---|---|---|
| POST | /auth/register | Create account; first account in an empty database is admin, later public signups are researchers |
| POST | /auth/login | Authenticate, issue access + refresh token |
| POST | /auth/refresh | Rotate access token |
| POST | /auth/logout | Revoke refresh token (Redis delete) |

### User Access (admin only)
| Method | Endpoint | Purpose |
|---|---|---|
| GET | /users | List accounts without password hashes |
| POST | /users | Create an account with an admin-assigned role |
| DELETE | /users/:id | Delete an account; the signed-in admin and last admin are protected |

### Dashboard
| Method | Endpoint | Purpose |
|---|---|---|
| GET | /dashboard/summary | Cached aggregate: active cultures, incubators currently out of range, today's pending schedule items, open contaminations, ongoing experiments |

### Incubator Monitoring
| Method | Endpoint | Purpose | Request Body |
|---|---|---|---|
| GET | /incubators | List incubators with latest reading + status | — |
| POST | /incubators | Add incubator | `{ name, target_temperature_c, target_co2_percent, target_humidity_percent }` |
| PATCH | /incubators/:id | Update targets/status | partial fields |
| GET | /incubators/:id/readings | Reading history (for chart) | — |
| POST | /incubators/:id/readings | Log a new reading (flags alert if out of range) | `{ temperature_c, co2_percent, humidity_percent }` |

### Media Preparation
| Method | Endpoint | Purpose | Request Body |
|---|---|---|---|
| GET | /media-batches | List media batches (supports `expiring_soon=true`) | — |
| POST | /media-batches | Log a newly prepared batch | `{ media_name, prepared_date, volume_prepared_ml, expiry_date, notes }` |
| PATCH | /media-batches/:id | Update remaining volume / notes | `{ volume_remaining_ml?, notes? }` |

### Cell Culture Management
| Method | Endpoint | Purpose | Request Body |
|---|---|---|---|
| GET | /cell-cultures | List cultures (filter by status/incubator) | — |
| GET | /cell-cultures/:id | Detail incl. current passage number | — |
| POST | /cell-cultures | Start a new culture | `{ culture_name, cell_line, incubator_id }` |
| PATCH | /cell-cultures/:id | Update status/incubator | `{ status?, incubator_id? }` |
| GET | /cell-cultures/:id/passages | Passage history | — |
| POST | /cell-cultures/:id/passages | Log a passage (bumps current_passage_number) | `{ passage_number, passage_date, confluency_percent, notes }` |

### Culture Scheduling
| Method | Endpoint | Purpose | Request Body |
|---|---|---|---|
| GET | /schedules | List scheduled tasks (filter by date range, culture, status) | — |
| POST | /schedules | Create a scheduled task | `{ cell_culture_id, task_type, scheduled_date, assigned_to, notes }` |
| PATCH | /schedules/:id | Mark completed/missed, edit | `{ status?, scheduled_date?, notes? }` |
| DELETE | /schedules/:id | Cancel a scheduled task | — |

### Contamination Logs
| Method | Endpoint | Purpose | Request Body |
|---|---|---|---|
| GET | /contamination-logs | List (filter by status) | — |
| POST | /cell-cultures/:id/contamination | Report contamination (also sets culture status) | `{ description }` |
| PATCH | /contamination-logs/:id | Resolve | `{ resolution_notes, status }` |

### Experiment Tracking
| Method | Endpoint | Purpose | Request Body |
|---|---|---|---|
| GET | /experiments | List experiments (filter by status/culture) | — |
| GET | /experiments/:id | Detail incl. observation count | — |
| POST | /experiments | Create experiment | `{ title, objective, cell_culture_id, start_date }` |
| PATCH | /experiments/:id | Update status/end_date | `{ status?, end_date?, objective? }` |

### Experiment Observations
| Method | Endpoint | Purpose | Request Body |
|---|---|---|---|
| GET | /experiments/:id/observations | List observations for an experiment | — |
| POST | /experiments/:id/observations | Add an observation | `{ description, measurement_value?, measurement_unit? }` |
| PATCH | /observations/:id | Edit an observation | partial fields |

## 6. Redis Usage

Kept to a small number of concrete jobs, each directly tied to a required module:

| Use case | Structure | Why |
|---|---|---|
| **Refresh token / logout revocation** | `String` `refresh:<userId>` with `EXPIRE` matching token TTL | Standard, easy-to-demo session control; instant logout via key delete. |
| **Incubator out-of-range alert flag** | `String` `incubator-alert:<incubatorId>` set (with short TTL, e.g. 1 hr) whenever a logged reading falls outside the incubator's target range ± tolerance | Directly demonstrates the Incubator Monitoring requirement: the dashboard/incubator list reads these flags instead of recomputing "is it currently out of range" from the readings table on every request. Easy to demo live: log an out-of-range reading, watch the alert appear on the dashboard immediately. |
| **Dashboard summary cache** | `String` (JSON) `cache:dashboard-summary`, TTL ~30–60s | Dashboard aggregates counts across 5+ collections; caching avoids recomputation on every visit, invalidated naturally by TTL. |

This satisfies "at least one meaningful, easy-to-demonstrate use" with room to spare, without stretching Redis into jobs it doesn't need to do for this scope.

*(Optional, not required for MVP: caching the incubator reading-history list for the chart view; a Redis Sorted Set for "media expiring soon" lookups.)*

## 7. Docker Services

The Compose file starts two infrastructure services:

1. **`mongodb`** — `mongo:7`, persistent `mongodbdata` volume, host port `27017` by default.
2. **`redis`** — `redis:7-alpine`, host port `6379`; no Redis-backed backend features are implemented yet.

The React/Vite frontend and Express API are started with their npm scripts in separate terminals. The local API connects to MongoDB through `MONGODB_URI` (default `mongodb://127.0.0.1:27017/cellculture_db`).

## Optional Features — Do NOT Build Unless Extra Time Remains

- Equipment booking, centrifuges, biosafety cabinets, freezer/storage-location management — **out of scope entirely**, not part of the brief.
- Separate cell-line master table / lot-and-supplier tracking for reagents beyond `media_batches`.
- Real IoT sensor integration for incubators — manual/simulated reading entry is sufficient for MVP.
- Real-time push updates (WebSockets) for incubator readings or schedule changes — polling/manual refresh is fine.
- Email/SMS notifications for alerts (out-of-range incubator, missed schedule, expiring media) — dashboard badges only.
- File/image uploads (e.g., attaching microscopy images to observations).
- Fine-grained per-resource permissions beyond the admin and researcher roles.
- Full audit logging of every mutation across every table.
- Analytics/reporting with charts beyond the incubator reading chart and dashboard counts.
- CI/CD pipeline, container orchestration beyond Compose, production secrets management.
- Comprehensive automated test coverage — test only the riskiest logic (auth, incubator alerting, passage/schedule state transitions).
